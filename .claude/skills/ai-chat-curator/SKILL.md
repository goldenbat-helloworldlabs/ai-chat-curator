# ai-chat-curator 오케스트레이터

## 실행 모드: 서브에이전트 위임

Pixel Agents가 `Agent` 도구 호출만 별도 캐릭터로 보여 주므로, 수집·정리·교차 확인·작성·검증을 모두 `Agent` 호출로 나눈다. `Workflow`는 쓰지 않는다. 단계 사이에서 사람 확인과 재작성 판단이 필요하기도 하다.

- 메인(이 스킬을 읽은 세션)이 조율·옵션 해석·파일 저장·스펙 기록·사람 확인을 맡는다
- `Agent` 호출의 `description`은 아래 표의 짧은 한국어를 **그대로** 쓴다. 캐릭터 말풍선에 그대로 표시된다
- 병렬 단계는 한 메시지에 `Agent`를 여러 번 넣는다. 서브에이전트는 백그라운드에서 돌고, 완료 알림이 오면 다음 단계로 간다. 알림 전에 결과를 단정하지 않는다

## 에이전트 구성

| 단계 | `subagent_type` | `description`(말풍선) | 스킬 | 산출물 |
| --- | --- | --- | --- | --- |
| 수집 a | `ai-chat-curator_collector` | `공식 발표 수집` | `ai-chat-curator.collect` | `01_collector_a.json` |
| 수집 b | `ai-chat-curator_collector` | `언론 기사 수집` | 〃 | `01_collector_b.json` |
| 수집 c | `ai-chat-curator_collector` | `커뮤니티 글 수집` | 〃 | `01_collector_c.json` |
| 수집 d | `ai-chat-curator_collector` | `실무자 글 수집` | 〃 | `01_collector_d.json` |
| 정리 | `ai-chat-curator_curator` | `글감 후보 정리` | `ai-chat-curator.curate` | `02_curator_candidates.json` |
| 교차 확인 | `ai-chat-curator_fact-checker` | `사실 교차 확인` | `ai-chat-curator.verify` | `03_fact-checker_{1,2}.json` |
| 작성 | `ai-chat-curator_writer` | `카톡 문안 작성` / 재작성 `카톡 문안 재작성` | `ai-chat-curator.write` | `04_writer_candidates.md`, `04_writer_drafts.md` |
| 검증 | `ai-chat-curator_reviewer` | `카톡 문안 검증` | `ai-chat-curator.review` | 응답 JSON → 메인이 `05_reviewer_round{r}.json`로 저장 |

데이터 형식은 `references/data-schema.md`. 경로 표기
- 하네스 폴더 `H` = 이 프로젝트 폴더(= GitHub 저장소 루트). 로컬에서는 `$HARNESS_ROOT/ai-chat-curator`, 클라우드에서는 받아 온 저장소 폴더
- 실행 폴더 `RUN` = `H/.ai-chat-curator/runs/{YYYY-MM-DD}_{n}/`
- 최종 폴더 `OUT` = `H/outputs/{YYYY-MM-DD}/`(같은 날 두 번째 실행이면 `{YYYY-MM-DD}_2/`)
- 게시 기록 `H/posted.md`, 반응 기록 `H/inputs/feedback.md`
- 모든 경로는 `H` 기준이라 `$HARNESS_ROOT`가 없어도 된다(클라우드 실행). 2026-11-23까지의 옛 위치 `$HARNESS_ROOT/outputs/ai-chat-curator/`·`$HARNESS_ROOT/inputs/ai-chat-curator/`는 더 쓰지 않는다

## 공통 규칙

- 모든 산출물·응답은 한국어
- 오픈채팅방에는 게시·전송하지 않는다. 수동 실행은 문안을 보여 주는 데서 끝나고, 자동 실행만 `scripts/slack.py`로 **사용자 개인 슬랙 DM**에 보낸다
- 슬랙 웹훅 주소는 환경 변수 `SLACK_WEBHOOK_URL`로만 다룬다. 파일·커밋·채팅·메시지에 값을 쓰지 않는다
- 스펙은 내부 산출물이다. `OUT`의 파일과 문안에 스펙 번호를 드러내지 않는다
- 스펙·`posted.md`·`CLAUDE.md`는 메인만 쓴다. 서브에이전트에게 쓰게 하지 않는다
- 게시 기록의 기준은 GitHub 저장소다. 자동 실행이 매일 `posted.md`를 커밋하므로, 수동 실행은 시작할 때 `git pull`, 끝나면(7·9단계 뒤) 바뀐 파일을 커밋·push한다. 저장소가 아직 연결되지 않았으면 건너뛴다

## 작업 절차

### 0단계: 요청 분류 · 스펙 · CLAUDE.md

1. **요청 분류**
   | 요청 | 처리 |
   | --- | --- |
   | 새 글감 요청("오늘 글감 찾아줘", "팁 위주로" 등) | 1단계부터 전체 실행 |
   | 직전 실행 문안 수정("2번 더 짧게", "3번 다른 걸로") | 가장 최근 `RUN`을 찾아 6단계(재작성 → 검증)만 다시. 후보 교체면 작성자에게 다음 순위 후보로 바꾸라고 지시 |
   | 게시 결과 알림("1, 3번 올렸어", "2번은 안 올림") | 9단계의 게시 기록 갱신만 |
   | 반응 기록 반영("feedback 반영해서 다시") | 1단계부터 실행하되 반응 요약을 새로 만든다 |
   | 자동 실행("ai-chat-curator 자동 실행", 클라우드 예약 실행) | `references/auto-mode.md`를 읽고 그 절차로 끝까지 실행한다. 묻지 않고 기다리지 않는다 |
   | 자동 실행 결과 확인("오늘 자동 실행 어떻게 됐어") | `git pull` 후 최신 `RUN`의 `06_main_autopick.json`·`99_main_failure.md`와 이번 달 자동 스펙 로그를 읽어 보고 |
   | "오늘 거 올렸어"(자동 발송분) | `git pull` 후 그날 `제안` 행을 `게시`로 바꾸고 커밋·push |
   | 하네스 자체를 고쳐 달라는 요청 | `sharness:evolve` 스킬로 넘긴다 |
2. **스펙 개설·귀속** — `H/specs/index.md`를 읽고 `references/spec-tracking.md` 규칙대로 귀속한다. 새 글감 요청은 새 스펙(`NNN-curate-YYYYMMDD` 등)을 In Progress로 연다. 직전 실행 문안 수정·게시 결과 알림은 그 실행의 스펙 실행 로그에 한 줄 추가한다. 스펙 번호를 `RUN/00_main_options.json`의 `spec` 필드에도 적는다
3. **출력 폴더 `CLAUDE.md` 확인** — 이 하네스는 `H`가 실행 프로젝트다. `H/CLAUDE.md`가 있는지 확인하고, 없으면 `$HARNESS_ROOT`의 연결 정보 양식(목표·호출 조건·원본·산출물·변경 이력)으로 만든다

### 1단계: 옵션 해석과 준비 (메인)

1. 요청에서 실행 옵션을 정한다. 지정이 없으면 기본값
   | 옵션 | 기본값 | 요청 예 → 해석 |
   | --- | --- | --- |
   | 기간 | 최근 7일(오늘 포함) | "이번 달" → 이번 달 1일~오늘, "지난주" → 지난주 월~일, "어제 이후" → 어제~오늘 |
   | 문안 개수 | 3~5 | "2개만" → 2, "많이" → 5 |
   | 유형 초점 | 없음(섞기) | "팁 위주로" → `업무 팁`, "질문거리 몇 개" → `질문거리` |
   | 도구 초점 | 없음(세 도구 공평) | "Claude 소식만" → 도구 `Claude` + 유형 초점 `소식` |
   | 관점 | a·b·c·d 전부 | "공식 발표만" → a만 |
2. `RUN`을 만든다(같은 날 기존 실행이 있으면 `_{n}` 증가). `00_main_options.json`을 쓴다
3. **반응 요약** — `feedback.md`를 읽어 `RUN/00_main_feedback.md`에 다음을 정리한다. 파일이 없거나 예시뿐이면 "반응 기록 없음 — 기본 비중"이라고 쓴다. 최근 2주 기록을 더 크게 본다
   - 좋았던 유형·주제, 별로였던 유형·주제(건수와 날짜)
   - 말투 요청(예: 더 짧게, 이모지 줄이기)
   - 원하는 주제
4. 게시 기록에서 최근 90일 링크를 뽑는다: `python -I .claude/skills/ai-chat-curator/scripts/curator.py posted-list --days 90`. 수집자 프롬프트에 링크 목록으로 넣는다

### 2단계: 관점별 수집 (병렬 4건)

한 메시지에 `Agent` 4번(옵션에서 관점을 줄였으면 그만큼). 프롬프트 틀:

```
관점: {a|b|c|d} ({공식 발표|언론|커뮤니티·게시판|실무자 글})
기간: {from} ~ {to}
실행 옵션: 유형 초점 {…}, 도구 초점 {…}
결과 파일: {RUN}/01_collector_{관점}.json
이미 제안·게시한 링크(다시 가져오지 말 것): {목록}
.claude/skills/ai-chat-curator.collect/SKILL.md를 읽고 따르라.
```

완료 알림마다 스펙 실행 로그에 "수집 {관점}: N건"을 남긴다. 네 건이 모두 끝나야 3단계로 간다.

### 3단계: 후보 정리 (1건)

```
실행 폴더: {RUN}
읽을 파일: 00_main_options.json, 00_main_feedback.md, 01_collector_{a,b,c,d}.json
게시 기록: {H}/posted.md (curator.py posted-list로 읽기)
결과 파일: {RUN}/02_curator_candidates.json
.claude/skills/ai-chat-curator.curate/SKILL.md를 읽고 따르라.
```

### 4단계: 사실 교차 확인 (병렬 1~2건)

메인이 `02_curator_candidates.json`에서 `needs_verification: true`인 후보 ID를 뽑는다(추천 후보 먼저). 6건 이하면 1건, 넘으면 둘로 나눠 한 메시지에 2건 호출한다. 확인할 후보가 없으면 이 단계를 건너뛰고 로그에 남긴다.

```
후보 파일: {RUN}/02_curator_candidates.json
맡은 후보: {C01, C04, …}
기간: {from} ~ {to}
결과 파일: {RUN}/03_fact-checker_{1|2}.json
.claude/skills/ai-chat-curator.verify/SKILL.md를 읽고 따르라.
```

### 5단계: 문안 작성 (1건)

```
실행 폴더: {RUN}
읽을 파일: 00_main_options.json, 00_main_feedback.md, 02_curator_candidates.json, 03_fact-checker_*.json
문안 개수: {min}~{max}
결과 파일: 04_writer_candidates.md, 04_writer_drafts.md
.claude/skills/ai-chat-curator.write/SKILL.md를 읽고 따르라.
```

### 6단계: 검증과 재작성 (최대 3회차)

1. 검증자 호출(`카톡 문안 검증`). 프롬프트에 `RUN`, 회차 `r`, `posted.md` 경로, `.claude/skills/ai-chat-curator.review/SKILL.md`를 따르라는 지시를 넣는다
2. 응답 JSON을 `RUN/05_reviewer_round{r}.json`에 저장한다. JSON이 깨졌으면 같은 프롬프트로 한 번 더 호출한다
3. 모두 통과하고 `run_level`도 통과면 7단계로
4. 반려가 있으면 작성자를 다시 호출한다(`카톡 문안 재작성`): 반려 번호와 `05_reviewer_round{r}.json` 경로를 주고 그 문안만 고치게 한다. 그 뒤 1로 돌아간다
5. 3회차에도 반려된 문안은 `04_writer_drafts.md`에서 빼지 말고 **사람에게 보여 줄 때 "검증 미통과"와 사유를 붙여** 따로 표시한다. 통과 문안이 3개 미만이어도 억지로 채우지 않는다

회차마다 스펙 실행 로그에 "검증 r회차: 통과 n / 반려 m(항목)"을 남긴다.

### 7단계: 산출물 저장과 게시 기록 (메인)

1. `OUT`을 만들고 복사한다
   - `RUN/04_writer_candidates.md` → `OUT/01_후보목록.md`
   - `RUN/04_writer_drafts.md` → `OUT/02_게시문안.md`(검증 미통과 문안은 맨 아래 「검증 미통과」 절로 옮기고 사유를 붙인다)
2. 게시 기록에 통과 문안만 `제안` 상태로 추가한다(`--only`에 통과 번호)

   ```bash
   python -I .claude/skills/ai-chat-curator/scripts/curator.py posted-add "{RUN}/04_writer_drafts.md" --date {오늘} --only {통과 번호들}
   ```
3. **스펙 마감** — 실행 로그에 산출물 경로를 남기고 완료 기록(산출물 경로, 검증 결과 요약, 누락·미통과, 후속 제안) → 상태 `Done` → `specs/index.md` 갱신. 8단계 이후 사람 응답은 같은 스펙의 실행 로그에 이어 적는다

### 8단계: 사람 확인 — 결과를 보여 주고 기다린다

채팅에 다음을 보여 주고 **응답을 기다린다(턴을 끝낸다).** 묻지 않고 다음 단계로 넘어가지 않는다.

- 한 줄 요약: 기간, 후보 N건, 문안 K건, 유형·도구 구성, 반응 기록 반영 여부
- 문안 전체: 번호·제목·유형·도구·검증 상태, 그리고 `kakao` 블록 내용을 그대로(사람이 바로 복사할 수 있게 코드 블록으로)
- 검증 미통과 문안이 있으면 사유와 함께 따로
- 후보 목록은 파일 경로만(표 전체를 다시 붙이지 않는다)
- 마지막 질문: "올릴 문안 번호, 고칠 점, 빼고 싶은 문안을 알려 주세요. 올린 뒤 '1, 3번 올렸어'라고 하시면 게시 기록을 갱신합니다."

스펙은 7단계에서 이미 마감했다. 이후 응답은 같은 스펙의 실행 로그에 이어 적는다.

### 9단계: 응답 처리와 마감

1. **사람 응답 처리**
   - 수정 요청 → 6단계 재작성·검증만 다시 하고, `OUT/02_게시문안.md`를 갱신한 뒤 바뀐 문안만 다시 보여 준다. 이 문안들은 이미 `posted.md`에 `제안`으로 들어가 있으므로, 작성자·검증자 프롬프트에 "`check-drafts`에 `--ignore-proposed-on {제안한 날짜}`를 붙여 실행하라"를 넣는다(자기 자신을 중복으로 잡지 않게). 원문 링크가 바뀐 문안은 `posted-status`로 옛 행을 `보류`로 바꾸고 새 링크를 `posted-add --only`로 추가한다
   - "N번 올렸어" → `curator.py posted-status --link {원문} --status 게시`
   - "N번 안 올림" → `--status 보류`
   - 사람이 문안을 직접 고쳐 올렸다고 하면 게시 기록은 그대로 두고 상태만 바꾼다
   - 처리 결과를 그 실행 스펙의 실행 로그에 한 줄 남긴다
2. **`CLAUDE.md` 변경 이력** — `H/CLAUDE.md` 변경 이력은 하네스 구조가 바뀔 때만 쓴다. 글감 실행 기록은 스펙 대장이 맡으므로 실행마다 변경 이력을 늘리지 않는다. 단, 실행 중 설정(출처 목록·기본값)을 바꿨으면 한 줄 남긴다
3. 사용자 보고에 스펙 번호를 밝힌다(최종 산출물에는 넣지 않는다)

## 오류 처리

| 상황 | 대응 |
| --- | --- |
| 수집자 1명 실패·빈 결과 | 한 번 다시 호출한다. 또 실패하면 그 관점 없이 진행하고 후보 목록·최종 보고에 "{관점} 수집 실패"를 적는다 |
| 웹 검색 사용량 한도·권한 거부 | 다시 시도하지 않는다. 부분 결과 파일을 직접 열어 어디까지 됐는지 확인하고 `RUN/99_main_failure.md`에 적은 뒤 사용자에게 알린다. 한도라면 풀리는 시각도 알린다 |
| 교차 확인 실패 | 확인 못 한 후보는 `아직 공식 확인 안 됨`으로 둔다. 메인이 판정을 추측해 채우지 않는다 |
| 검증 응답이 JSON이 아님 | 한 번 다시 호출. 또 실패하면 메인이 `check-drafts` 결과만 보여 주고 "검증 에이전트 판정 없음"을 명시해 사람 확인으로 넘긴다 |
| 후보가 적음(예: 조용한 주간) | 억지로 채우지 않는다. 기간을 넓힐지 사용자에게 묻는다 |
| `posted.md` 형식 깨짐 | `posted-list`가 빈 목록을 내는데 파일에 내용이 있으면 사용자에게 알리고 손으로 고칠 줄을 보여 준다. 임의로 다시 쓰지 않는다 |
| 충돌하는 정보(매체마다 다른 날짜·내용) | 지우지 않고 출처별로 후보 문서에 남긴다. 공식 출처를 기준으로 쓴다 |

## 테스트 시나리오

### 정상 흐름
1. 사용자: "오늘 글감 찾아줘" → 기간 최근 7일, 문안 3~5, 초점 없음
2. 수집 4건 병렬(말풍선 `공식 발표 수집`·`언론 기사 수집`·`커뮤니티 글 수집`·`실무자 글 수집`) → 정리 1건 → 교차 확인 1~2건 → 작성 → 검증 1회차에서 문안 1건 반려(저작권) → 재작성 → 2회차 전원 통과
3. 결과: `OUT/01_후보목록.md`(후보 10개 내외), `OUT/02_게시문안.md`(문안 4개), `posted.md`에 4행 `제안` 추가, 채팅에 문안 4개를 보여 주고 대기
4. 사용자: "1, 3번 올렸어" → 두 행 상태 `게시`

### 범위 지정 흐름
1. 사용자: "Claude 소식만, 이번 달" → 기간 이번 달 1일~오늘, 도구 Claude, 유형 소식

### 오류 흐름
1. 커뮤니티 수집자가 웹 검색 한도로 빈 결과 → 재시도하지 않고 a·b·d로 진행, `99_main_failure.md`에 기록

3. 3회차에도 반려된 문안 1건 → 「검증 미통과」로 사유와 함께 보여 주고 게시 기록에는 넣지 않는다

### 자동 실행 흐름
1. 클라우드 예약 실행이 매일 10:00(KST) "ai-chat-curator 자동 실행"으로 부름 → `references/auto-mode.md`
2. 수집~검증은 같음 → `curator.py auto-pick`이 자격 있는 첫 문안 선택(예: 2026-11-23 실행이면 3번 Gemini Tasks. 1·2번은 사실 확인 반려 이력, 4번 질문거리, 5번 부분 확인이라 제외)
3. `posted.md`에 그 한 건만 `제안`, `slack.py send-draft`로 메모 한 통 + 문안 한 통 전송, 커밋·push
4. 자격 있는 문안이 없으면 쉼 알림 한 통, 게시 기록 추가 없음
